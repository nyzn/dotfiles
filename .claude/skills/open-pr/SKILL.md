# Open a PR

Push the current branch and open a pull request whose body is generated by the
`pr-description` skill, so every PR lands with a consistent what/why + how-to-test
description.

## Steps

1. **Pre-flight.** Confirm there are commits to open a PR for:
   `git status`, `git log <base>..HEAD --oneline`. If the working tree has
   uncommitted changes the user wants included, commit them first via the
   `conventional-commit` skill. Identify the base branch (default `main`).
2. **Push.** `git push -u origin <branch>` (retry on network error with backoff,
   per the repo git rules). Never push to a branch other than the designated one.
3. **Write the body.** Invoke the **`pr-description`** skill to produce the PR body
   from the actual diff (`git diff <base>...HEAD`). Do not hand-write the body —
   `pr-description` owns that format and the how-to-test section.
4. **Honor a template.** If the repo has a PR template
   (`.github/pull_request_template.md`, `.github/PULL_REQUEST_TEMPLATE.md`, root, or
   `docs/`), `pr-description` already maps onto it; keep those headings.
5. **Create the PR ready for review** using the GitHub MCP `create_pull_request`
   tool: title = the primary commit subject (Conventional Commits form), body from
   step 3, `draft: false`, base = the base branch. Do **not** open as a draft — this
   repo wants PRs ready for review on open.
6. **Reuse, don't duplicate.** If an *open* PR already exists for this branch,
   update its body instead of opening a second one. A merged/closed PR does not
   count — open a fresh one.
7. **Auto-review.** Immediately run the **`code-reviewer`** agent (Agent tool,
   `subagent_type: code-reviewer`) on the change. In the task prompt, tell it to
   diff with `git diff <base>...HEAD` — the branch is already pushed with a clean
   tree, so the agent's default bare `git diff` would show nothing. Surface its
   findings in the session grouped **Must fix / Should fix / Nit** (the agent's own
   format). If there are Must-fix findings, offer to resolve them via the `fix-pr`
   skill, acting on these in-session findings directly (they aren't posted as PR
   comments here); don't auto-push fixes without the user.
8. **Report** the PR URL. Subscribe to its activity if the session watches PRs.

## Notes

- **Ready for review, not draft** — pass `draft: false` to `create_pull_request`
  even if a default-draft convention exists elsewhere. The user can still convert to
  draft manually if needed.
- Every open runs the `code-reviewer` agent automatically (step 7); `review-pr`
  stays a separate path for marking findings as inline PR comments on demand.
- One PR per branch; scope to a single app per the monorepo convention.
- This skill composes: `conventional-commit` (commits) → `pr-description` (body) →
  `open-pr` (push + create + auto code-review). Then `fix-pr` iterates on findings.

## Checklist

- [ ] Commits exist and are on the designated branch
- [ ] Branch pushed with `-u origin <branch>`
- [ ] Body generated by the `pr-description` skill (not hand-written)
- [ ] Existing PR template honored if present
- [ ] Opened **ready for review** (not draft); no duplicate PR for the branch
- [ ] `code-reviewer` agent run on the diff and findings surfaced (Must/Should/Nit)
- [ ] PR URL reported
